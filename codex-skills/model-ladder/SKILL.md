# model-ladder

Run the user's task through the Codex runner. Implement it yourself only when the runner returns DIRECT, using the isolated draft and independent verification flow below.

1. Locate this SKILL.md on disk using the skill path supplied by Codex. Resolve ../../scripts/codex-run.mjs relative to its containing directory. Do not use CLAUDE_PLUGIN_ROOT or a guessed installation path.
2. If `MODEL_LADDER_HUD=1`, reuse the HUD already running in this terminal; do not start a watcher. Otherwise, unless `band: false` in `.codex/model-ladder.json` or `MODEL_LADDER_BAND=0`, start `scripts/watch.mjs --cwd <target-repo-root>` from the same package in a persistent PTY terminal and show that terminal using `open_in_codex` when available. Reuse this chat's existing watcher for the repository. Do not wait for the watcher to exit. On a surface without terminal panels, use runner progress output and explain the limitation. For an integrated CLI footer, install the package's npm dependencies and start `node scripts/codex-hud.mjs --cwd <target-repo-root> -- resume` before entering Codex. The wrapper launches Codex and cannot attach to this running session. Windows requires a native `codex.exe`; `CODEX_BINARY` can select its path.
3. Availability check, before the run: resolve `worker_skills` and `verifier_skills` with the exported `loadConfig(targetRepoRoot)` from the same packaged `codex-run.mjs`, then pick out every skill, plugin, slash command or MCP server they name (for example `ponytail`). Compare each with the skills, plugins and MCP tools available to this Codex session; ignore generic phrases such as "available UI/UX skills". For each name you cannot find, tell the user once, in their language, before running, for example "`ponytail` is not available in this project (it may not be installed, or only enabled elsewhere), so this run will not use it.", naming the role. This is a warning only: do not stop the run and do not edit the settings. If unsure, say so rather than claiming it is missing. Remember these names for the report.
4. Run that script with Node 20+ from the target Git repository root. Pass a JSON object with task and, only if already provided by the user, acceptance as an array of strings. Pass contextTokens and contextWindow only when actual values are available from the host or user; never estimate or read private transcripts to fill them. Otherwise omit them. forceLadder true disables DIRECT and split suggestions. On Windows PowerShell, write the JSON to a uniquely named UTF-8 file in the system temp directory under model-ladder/<repository hash>/ (resolve artifactDir(targetRoot) from the packaged scripts/common.mjs; `[IO.Path]::GetTempPath()` identifies only the base), never in the target repository or its .model-ladder directory, then pass --input <absolute-file-path> and delete that file once the run has ended. Use apply_patch or a literal here-string with .NET WriteAllText and UTF8Encoding to create the file; do not pipe non-ASCII text or Get-Content to Node because Windows PowerShell can replace it with question marks. On other shells, literal UTF-8 stdin is also supported. Never interpolate task text into shell code. The script also accepts a task as one argument.
5. Follow the JSON result. DIRTY means show files and ask whether to run on top of those uncommitted changes, then rerun with allowDirty true only after user authorization. NEEDS_INPUT means ask its message and rerun with the clarified task or the user's acceptance criteria. Never invent approval of criteria. NEEDS_INPUT with reason OVERLAP means another active Claude Code or Codex run works on overlapping files (listed in overlaps): ask whether to wait, and rerun the same JSON once the user says that run is done; if the user says a listed run is no longer running, rerun with clearStale set to its runId. Runs with non-overlapping scopes proceed side by side without asking. NEEDS_INPUT with reason SPLIT means the router estimated the task over split_minutes: in the user's language list splitSuggestion.estimatedMinutes, the limit and each part (task and scope), and ask: run in sequence / run the whole task / stop. Run in sequence means run the runner once per part, each with that part's task and the user's acceptance criteria, and start the next part only after the previous one returned VERIFIED (stop and report otherwise). Run the whole task means rerun the same JSON with acceptSplit false. Stop means end without running. STALE_RUN means inspect the listed lock files (.model-ladder/runs/<runId>.json, or an older version's .model-ladder/run.json) and their processes first, then rerun with clearStale true only after the user confirms. Do not clear a live run's lock. STOPPED means fix the stated environment or ask the necessary clarification before rerunning. ERROR and FAILED mean report the failure. CONFLICT means report the retained patch and worktree paths for review. VERIFIED means report the summary, verified checks, attempt cells and applied files. A report-only task returns its report in summary.
6. Report once, at the end, in the language the user uses in this session. Do not paste the runner's English JSON or summary text as is. Summarize the status, the changed files (applied or not), the verification result, and limits or follow-ups (retained worktree, patch, checkpoint or handoffPath, failed attempts). Keep file names, commands, paths, model names and status codes in their original form. If any role reported a missing skill, plugin or MCP server (in its summary, reasons or context), or step 3 found names missing, list them as capability blockers, naming the role.

If STOPPED includes errorCode TIMEOUT and resumeRun, rerun the same JSON with that resumeRun. Preserve the original task, acceptance and existing dirty-change consent. Resume at most twice automatically; after that, report the retained worktree and checkpoint. The runner validates the original checkout and configuration, seeds a new worktree from the unverified draft, and verifies the completed result before applying it. If those inputs changed, report the mismatch instead of starting over silently. Do not automatically resume CANCELLED runs or retry unresolved authentication, model-access or sandbox errors. Only VERIFIED exits with code 0; DIRTY, NEEDS_INPUT, STALE_RUN and DIRECT exit with code 2, so always inspect the JSON on nonzero exit. If STOPPED has errorCode USAGE_LIMIT (`usageGuard`, on by default, or Codex's own usage, rate or quota limit), do not resume automatically: report handoffPath, worktreePath and checkpointPath to the user and resume only after the quota resets.

Handoff: the runner always writes a template `.model-ladder/HANDOFF.md` on USAGE_LIMIT, and `node ../../scripts/watch.mjs --handoff --cwd <target-repo-root>` (path resolved as in step 1) writes one on demand. When STOPPED has errorCode USAGE_LIMIT, or the user asks for a handoff, you then rewrite `.model-ladder/HANDOFF.md` yourself from your whole conversation with the user, in the language the user uses in this session, with the sections `## Goal`, `## User preferences and decisions`, `## Done and not done`, `## Suggested next steps` and `## How to resume`. After them add `## Appendix: program-generated verification (authoritative)` and paste the template unchanged (minus its title line): task, attempts PASS/FAIL, status, paths and the JSON resume input. AI-written sections and program-generated data stay clearly separate, and the appendix wins where they differ. If Codex itself hit the hard usage limit and you cannot call the model again, keep the template as it is: it is the fallback. Do not run the runner again to do this.

For concurrent runs, use the run ID and per-run live state in the reported artifact folder to confirm whose data is being handed off. The shared live.json/panel and HANDOFF.md show the last writer. A force-killed process may retain a draft without a checkpoint or result.json; inspect it, resolve stale locks with consent, and restart the original input after quota reset. Do not invent resumeRun or claim a killed draft was verified.

If the sandbox rejects process-tree termination, report the failed run ID and shutdown blocker from stderr. Its active registration remains; do not claim that run stopped or clear a live lock. Use the run's normal terminal interrupt control where available. Never add bypass flags or substitute a weaker single-PID kill for the tree-stop requirement.

The same plugin package also supports Claude Code through /model-ladder:run. Codex uses this skill and its own settings: personal ones such as usageGuard in ~/.codex/model-ladder.json ($CODEX_HOME when set), project ones in .codex/model-ladder.json, which wins. Never change the user's usageGuard yourself; only the user turns it on or off (watch.mjs g, --guard, or editing the file). Defaults mirror the Claude defaults: gpt-6-luna for Haiku, gpt-5.6-terra for Sonnet and gpt-6.1-sol for Opus. If an account does not expose them, configure available model IDs and supported efforts. Unavailable models stop the run. Optional CODEX_BINARY names the native Codex executable. Keep the installed sandbox and approval controls. Never add bypass flags.

`worker_skills` and `verifier_skills` are natural-language skill instructions in `.codex/model-ladder.json`. For example, "When coding, use ponytail to review and simplify the code; when working on UI, use available UI/UX skills." Each line may start with `project: instructions`; the first colon always separates an exact main-repo folder name, unmatched lines are excluded, and lines without a colon are global. The runner passes only selected instruction bodies to roles, preserving later colons and line breaks; use these same effective values for availability checks. Each role evaluates conditions for its task, then selects relevant skills actually available in that session by reading and following their supplied SKILL.md paths. Existing skill-name values still work. Empty values and unresolved `${...}` placeholders add no instructions. Report an applicable required skill that is missing; never invent a name or claim use. Skill instructions cannot expand a role's scope or permissions, allow a verifier to fix code, or invoke model-ladder skills, workflows or runners recursively.

Successful changes are applied without committing by default. commit: true opts into committing verified files; pre-existing or concurrent edits in those files skip the commit with a note. Never enable commit on the user's behalf. Never push. Existing uncommitted changes are snapshotted without altering the user's Git index. Verification requires an existing configured/discovered test command or acceptance criteria explicitly supplied by the user. .model-ladder keeps only small shared files: runs/ (one lock per active run, runs/<runId>.json), history.jsonl, live.json, usage.json and HANDOFF.md; recommend ignoring that directory. Each run's attempt worktrees, logs, snapshots, checkpoint and result.json live in the system temp directory under model-ladder/<repository hash>/, and the paths in the result point there.

DIRECT is an unverified draft, never completion. Modify only result.worktreePath, obey result.protected and result.plan, preserve the user's changes, and never stage, commit, reset, switch branches or push. Follow worker_skills (test-writer rules apply when plan.allowTests is true). Then rerun the original JSON with directRun set to result.runId and directSummary containing your work and checks. The runner reclaims scope, validates the original base/config/task/acceptance, protects verification inputs, independently verifies, and applies only a passing result. A failed check can retry through normal workers. If the host sandbox cannot edit that artifact worktree, report the limitation and rerun with forceLadder true; never bypass the sandbox or edit the user checkout instead. A direct draft holds no active lock while the caller edits it; other runs may proceed, and re-entry rechecks overlap, baseline and patch applicability. The Codex panel has no automatic context-window data source and does not show context usage.
